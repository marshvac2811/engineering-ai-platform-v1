3. INPUT REQUIREMENT MODEL
============================================================

The framework should support:

1. Required input
2. Optional input
3. Conditional input
4. Derived input
5. AI-extracted input
6. User-confirmed input
7. Attachment-derived input
8. Governed default
9. Project override

The framework must distinguish:

MISSING
≠
DEFAULTED
≠
AI-INFERRED
≠
USER-CONFIRMED
≠
CALCULATED

This distinction is essential for engineering auditability.

============================================================
4. DYNAMIC QUESTION MODEL
============================================================

Questions should be generated from SkillDefinition rather than maintaining a
separate hard-coded question list for every skill.

Example:

Input:
  climate_zone

Definition:
  type = enum
  values = hot_dry, warm_humid, composite, moderate, cold

Generated question:
  "Which climate zone should be used?"

Conditional questions must also be supported.

Example:

cooling_tower:
  load_method = chiller
      → ask chiller_tr
      → ask chiller_cop

  load_method = direct
      → ask direct_load_kw

============================================================
5. AI RESPONSIBILITIES
============================================================

AI may:

- understand natural-language requests
- identify engineering domain
- select a registered skill
- extract facts from text
- identify likely missing information
- ask the questions defined by the skill
- interpret uploaded documents
- identify inconsistencies
- explain engineering results
- identify possible warnings
- request human confirmation
- prepare an engineering response

AI must NOT silently invent:

- engineering constants
- standards
- code requirements
- manufacturer limits
- design conditions
- safety factors
- missing project facts

Those must come from governed sources, user/project data, or deterministic
engineering definitions.

============================================================
6. DETERMINISTIC ENGINE RESPONSIBILITIES
============================================================

Existing calculators should remain responsible for:

- engineering formulas
- calculations
- unit conversions
- numerical validation
- engineering result generation
- calculation trace
- deterministic warnings

The framework should wrap these engines rather than rewrite them unnecessarily.

9. PERFECTION FILTER DESIGN
============================================================

The Perfection Filter should be a common platform layer.

It should check:

A. Input completeness
B. Input consistency
C. Units
D. Engineering ranges
E. Cross-field relationships
F. Standards availability
G. Assumption provenance
H. Calculation trace
I. Result completeness
J. Warning severity
K. Human-review requirement
L. Manufacturer verification requirement
M. Dispatch readiness

It must return structured findings rather than merely True/False.

Suggested finding:

- severity
- category
- field
- message
- evidence
- action_required
- blocking

============================================================
10. HUMAN REVIEW MODEL
============================================================

Human review should be determined by:

1. SkillDefinition default
2. Engineering risk
3. validation findings
4. standards status
5. manufacturer verification requirement
6. perfection-filter findings
7. project configuration

A skill should never bypass mandatory review merely because AI believes
the result is correct.

13. COMPATIBILITY REQUIREMENT
============================================================

The new framework must support existing skill implementations without forcing
an immediate rewrite of every calculator.

Preferred migration pattern:

SkillDefinition
      ↓
Common Skill Adapter / Wrapper
      ↓
Existing Skill Adapter
      ↓
Existing Deterministic Calculator

This permits gradual migration and reduces regression risk.

Current engine registration is manually maintained.

Future design should allow:

registry.yaml
      ↓

      ↓

      ↓
runtime registration

The framework should detect:

- registered but not executable
- executable but not registered
- duplicate skill IDs
- missing implementation
- invalid definition
- unsupported execution type
